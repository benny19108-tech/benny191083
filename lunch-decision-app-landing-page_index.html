智能午餐決策 App

午餐神隊友

專為中午面臨選擇障礙的學生與上班族打造的智能午餐決策 App，透過快速條件篩選、隨機盲抽與個人化推薦機制，讓使用者在三分鐘內解決「今天中午吃什麼」的難題。

使用者故事 (User Stories)

情境一（快速決策）

作為趕時間的上班族，我想要輸入預算與步行距離後由系統隨機推薦一家餐廳，以便快速結束猶豫並準時返回工作崗位。

情境二（飲食篩選）

作為有特殊飲食偏好或過敏需求的學生，我想要設定忌口標籤與飲食類型來自動過濾搜尋結果，以便安全且精準地找到符合當下需求的店家。

情境三（探索嘗鮮）

作為喜歡發掘新店的外食族，我想要查看附近其他使用者分享的熱門清單或隨機抽籤主題包，以便打破日常鬼打牆的覓食習慣。

系統架構與層級

1

展示層 (Presentation Tier / 前端 Client)

這是使用者在手機或瀏覽器上直接操作的畫面與互動介面。

畫面呈現：提供「一鍵盲抽」、「條件/心情/天氣篩選器」、「店家地圖與卡片頁面」以及「歷史紀錄清單」。

互動邏輯：當使用者打開 App 時，展示層會取得手機目前的 GPS 定位，並允許使用者點選當下心情（如：暴怒、想犒賞自己）。當按下「開始抽籤」時，前端不會在手機裡進行複雜的運算，而是打包定位資訊與篩選條件，發送 HTTP 請求（API Call）給應用邏輯層，最後將後端傳回的餐廳結果繪製成抽籤動畫呈現給使用者。

2

應用邏輯層 (Application Tier / 後端 Server)

這是整個系統的運算大腦與業務邏輯核心，負責調度資料與執行決策演算法。

天氣與地理調度：收到前端傳來的 GPS 後，先呼叫外部 OpenWeather API 取得當前氣溫與降雨狀態；同時呼叫 Google Maps / Places API 撈取周邊指定距離內的店家清單。

加權盲抽演算法：

  • 硬性過濾：比對資料庫，排除店家營業狀態為歇業、符合使用者忌口標籤（如：素食者排除肉類）、以及設定為「近 3 天排除」的店家。
  • 動態加權：結合天氣與心情邏輯進行權重計算（例如：若「天氣暴雨」，將 300 公尺內的店家權重 ×2.0；若心情選「暴怒」，將重口味/麻辣類別權重 ×1.5）。
  • 隨機抽籤：根據最終計算出的權重池進行隨機抽樣，選出 1 家最佳餐廳回傳給展示層。
3

資料層 (Data Tier / 資料庫 Database & Cache)

這是長期儲存資料與加速查詢的倉庫。

主資料庫 (RDBMS / PostgreSQL)：

  • 使用者資料：記錄帳戶資訊、個人化偏好（預設步行時間、忌口條件）。
  • 標籤與屬性庫：儲存所有餐廳對應的「心情」、「天氣」與「飲食類別」標籤對照表。
  • 決策歷史紀錄：記錄每一次抽籤結果、使用者給予的評分，以及是否勾選「3 天內不再抽到」的標記。

快取資料庫 (Cache / Redis)：

用於快取熱門區域的 Google 店家資料或天氣資訊，避免每次盲抽都頻繁呼叫付費的外部 API，進而降低營運成本並大幅提升 App 載入速度。

系統狀態與流程

待命階段 (Idle)

App 開啟後處於準備狀態，呈現心情標籤與篩選設定。此時「開始盲抽」按鈕處於可點擊狀態。

運算與請求階段 (Fetching)

使用者點擊「開始盲抽」後，系統立即鎖定按鈕（防止重複連點），同時向背景發起請求，取得地理位置、天氣資料，並進行店家權重運算與抽籤。

結果展示階段 (ResultShown)

後端成功回傳最佳店家後，系統切換至展示狀態，繪製店家資訊卡片、導航按鈕，並重新解鎖操作按鈕。

異常處理階段 (ErrorState)

若因網路超時或條件設定過度嚴格導致無符合店家，系統彈出錯誤提示，並引導使用者重試或放寬搜尋條件。

狀態重置與轉移

  • 點擊「不喜歡？重新盲抽」：將當前店家納入臨時排除清單，直接切回運算階段重新抽籤。
  • 點擊「導航 / 返回」：寫入歷史決策紀錄，重置頁面狀態並切回待命階段。
